## 1. Разбор знакомого сервиса: Маркетплейс (на примере Ozon)

Для анализа выбрано мобильное приложение и веб-интерфейс маркетплейса Ozon.

### Действие 1: Добавление товара в корзину
* **Что уходит на сервер:** Идентификатор товара (product_id), выбранное количество (quantity) и токен авторизации пользователя (из которого бэкенд извлекает user_id).
* **Что проверяет сервер:** Авторизован ли пользователь, существует ли данный товар в системе и есть ли он прямо сейчас в наличии на складе в указанном количестве.
* **Куда это сохраняется:** В базу данных, в таблицу корзины пользователей (например, `cart_items` или `user_baskets`), где обновляется или создается запись для связки конкретного пользователя и товара.
* **Что возвращается обратно:** Статус успешного выполнения (HTTP 200 OK), обновленное общее количество товаров в корзине и их суммарная стоимость для отображения на иконке корзины.

### Действие 2: Оформление и создание заказа (нажатие кнопки «Оформить заказ»)
* **Что уходит на сервер:** Список id товаров из корзины, выбранный id пункта выдачи (delivery_point_id), выбранный способ оплаты (payment_method) и примененные промокоды.
* **Что проверяет сервер:** Не изменилась ли цена товаров за время сборки корзины, доступны ли пункты выдачи, актуальны ли остатки на складе (блокируется ли товар под этот заказ) и валиден ли промокод.
* **Куда это сохраняется:** В базе данных создается новая запись в таблице заказов (`orders`) со статусом «Создан / Ожидает оплаты», а также записи в связующей таблице состава заказа (`order_items`). В таблице остатков товаров на складе уменьшается доступное количество.
* **Что возвращается обратно:** Уникальный номер заказа (`order_id`) и ссылка/данные для перехода на платежный шлюз (или статус успеха, если выбрана оплата при получении).

### Действие 3: Написание и отправка отзыва к купленному товару
* **Что уходит на сервер:** Идентификатор товара (product_id), оценка в звездах (rating), текстовый комментарий (text) и массивы медиафайлов (фотографии/видео), если они прикреплены.
* **Что проверяет сервер:** Действительно ли данный пользователь покупал этот товар и забрал его из пункта выдачи, не превышает ли текст лимит по символам, прошел ли текст автоматический фильтр стоп-слов.
* **Куда это сохраняется:** В базу данных в таблицу отзывов (`reviews`) со статусом «На модерации». Сами фотографии сохраняются в облачное объектное хранилище (например, S3), а в БД записываются ссылки на них.
* **Что возвращается обратно:** Статус успешного приема отзыва (HTTP 201 Created) и всплывающее уведомление для пользователя о том, что отзыв отправлен на проверку модераторам.

## 2. Поиск места для отказа

Для анализа устойчивости выбрано **Действие 2: Оформление и создание заказа**.

* **Если пропадёт сеть на середине пути:**
  * *Предположение:* Если сеть пропала до отправки, запрос не уйдет. Если в момент отправки — сервер может создать заказ, но клиент об этом не узнает. Без механизмов проверки (транзакций и идемпотентности) это может привести к списанию денег без отображения заказа у пользователя.
  * *Поведение на практике:* Приложение Ozon выдает ошибку «Проблемы с интернетом» и блокирует интерфейс. Если запрос успел дойти до сервера, при восстановлении сети и обновлении страницы заказ появляется в разделе «Мои заказы» как неоплаченный, повторного списания не происходит благодаря механизму транзакций на бэкенде.
* **Если нажать кнопку дважды:**
  * *Предположение:* На сервер уйдут два идентичных запроса. Если бэкенд не умеет обрабатывать дубли, в базе данных создадутся два одинаковых заказа, а с пользователя спишется двойная сумма.
  * *Поведение на практике:* На клиенте кнопка «Оформить» сразу после первого клика переходит в состояние `disabled` (становится неактивной) и запускается анимация загрузки. На бэкенде используется ключ идемпотентности (уникальный хэш корзины) — если второй запрос все же прорывается, сервер видит дубликат и просто возвращает результат первого запроса.
* **Если отправить пустое поле (например, убрать пункт выдачи через консоль разработчика):**
  * *Предположение:* Если на бэкенде нет валидации входных данных, пустой `delivery_point_id` уйдет в базу данных, что вызовет ошибку SQL (`NOT NULL constraint violation`) и приведет к падению сервера с ошибкой 500 (Internal Server Error).
  * *Поведение на практике:* Интерфейс приложения физически не дает нажать кнопку, подсвечивая поле выбора адреса красным. При попытке отправить пустой запрос напрямую через API, бэкенд мгновенно возвращает ошибку валидации HTTP 400 Bad Request с описанием: `"delivery_point_id является обязательным полем"`. Сервер работает стабильно.
